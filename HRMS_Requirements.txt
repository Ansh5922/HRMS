1.1 PRODUCT NAME
    IntelliHR — AI-Powered Human Resource Management System

1.2 PRODUCT DESCRIPTION
    IntelliHR is a comprehensive, AI-augmented Human Resource Management System
    designed to streamline and automate the entire employee lifecycle within an
    organization. It serves as the single source of truth for all HR operations,
    from recruitment and onboarding to payroll, performance management, and
    offboarding.

    The system is built with a dual-backend architecture:
      - A high-performance Go (Golang) core backend handling all primary
        business logic, APIs, and data operations.
      - A Python FastAPI AI backend specializing in machine-learning features
        such as facial recognition-based attendance and a RAG-powered AI
        assistant.

    IntelliHR is accessible across platforms:
      - A React.js web dashboard for HR administrators, managers, and executives.
      - A React Native mobile application for employees and field managers.

    The database layer uses PostgreSQL with the pgvector extension to support
    both relational HR data and vector embeddings required for the AI features.

MODULE 9: AI CHATBOT — RAG-BASED HR ASSISTANT
────────────────────────────────────────────────────────────────────────────────
Description:
    An intelligent HR assistant powered by a Retrieval-Augmented Generation
    (RAG) pipeline. Employees and HR staff can query HR policies, get
    payslip summaries, check leave balances, understand processes, and get
    personalized answers — all through a conversational interface on web
    and mobile.

Features:
    9.1  Natural language query interface (chat UI)
    9.2  RAG over HR documents (policies, handbooks, SOPs, FAQs)
    9.3  Personalized responses using employee context (leave balance,
         payslip, attendance)
    9.4  Conversation history per user session
    9.5  Document ingestion pipeline (PDF/DOCX → chunks → embeddings)
    9.6  Admin panel to upload/manage knowledge base documents
    9.7  Confidence score and source citations in responses
    9.8  Fallback to HR ticket creation on unanswered queries
    9.9  Multi-language support (English + regional languages)
    9.10 Voice input support (mobile app)

Technical Architecture (FastAPI):
    - Document ingestion: PyPDFLoader → text splitting → embedding
      via OpenAI/local model → store in pgvector
    - Query flow: User query → embedding → pgvector similarity search
      → top-K chunks → LLM prompt → response
    - LLM: OpenAI GPT-4o / Ollama (self-hosted llama3)
    - Embedding model: text-embedding-3-small / instructor-xl
    - Framework: LangChain with PGVector retriever

Database Entities:
    - kb_documents (id, title, file_url, category, ingested_at,
                    chunk_count, org_id)
    - kb_chunks (id, doc_id, content, embedding vector(1536),
                 metadata jsonb)  -- pgvector
    - chat_sessions (id, user_id, started_at)
    - chat_messages (id, session_id, role [user/assistant],
                     content, retrieved_chunks jsonb, created_at)

API Endpoints (FastAPI):
    POST   /ai/v1/chat/message       → Send message, get RAG response
    GET    /ai/v1/chat/history/:sid  → Get session history
    POST   /ai/v1/chat/session       → Create new session
    POST   /ai/v1/kb/upload          → Upload document to knowledge base
    GET    /ai/v1/kb/documents       → List knowledge base docs
    DELETE /ai/v1/kb/documents/:id   → Remove document + chunks

════════════════════════════════════════════════════════════════════════════════

Following the prescribed workflow:
    Database Schema → DB Creation → DB Integration → Module Development
    → Face Recognition → FastAPI ↔ Go Integration → Frontend + Chatbot
    → Deployment

────────────────────────────────────────────────────────────────────────────────
PHASE 1: DATABASE SCHEMA DESIGN (Week 1–2)
────────────────────────────────────────────────────────────────────────────────
Deliverables:
    □ Complete ER diagram for all 12 modules
    □ PostgreSQL DDL scripts for all tables
    □ pgvector extension setup and vector column definitions
    □ Seed data scripts (roles, permissions, leave types, etc.)
    □ Database migration tool selection: golang-migrate or goose

Tasks:
    1. Define all entities and relationships (ERD in dbdiagram.io)
    2. Write CREATE TABLE SQL scripts with constraints and indexes
    3. Add pgvector extension: CREATE EXTENSION IF NOT EXISTS vector;
    4. Define face_embeddings and kb_chunks tables with vector columns
    5. Design indexes (B-tree for FKs, HNSW for vector similarity)
    6. Write migration files (000001_init_schema.up.sql, etc.)
    7. Write seed scripts for roles, permissions, leave types, holidays
    8. Peer review all schema decisions

Directory Structure:
    /database
    ├── migrations/
    │   ├── 000001_auth_schema.up.sql
    │   ├── 000002_employee_schema.up.sql
    │   ├── 000003_attendance_schema.up.sql
    │   └── ... (one file per module)
    ├── seeds/
    │   ├── roles.sql
    │   ├── permissions.sql
    │   └── leave_types.sql
    └── ERD.dbml

────────────────────────────────────────────────────────────────────────────────
PHASE 2: DATABASE CREATION (Week 2)
────────────────────────────────────────────────────────────────────────────────
Deliverables:
    □ PostgreSQL instance running (Docker or cloud RDS)
    □ pgvector installed and verified
    □ All migrations applied and verified
    □ Seed data loaded
    □ Backup/restore procedure documented

Tasks:
    1. Set up PostgreSQL 16 via Docker Compose
    2. Install pgvector: git clone → make install
    3. Create databases: hrms_dev, hrms_test, hrms_prod
    4. Run migrations (golang-migrate up)
    5. Verify all tables, indexes, and vector columns
    6. Load seed data and verify
    7. Set up pg_hba.conf with secure access rules
    8. Configure connection pooling with PgBouncer

────────────────────────────────────────────────────────────────────────────────
PHASE 3: DATABASE INTEGRATION TO BOTH BACKENDS (Week 3)
────────────────────────────────────────────────────────────────────────────────

Go Backend Integration:
    1. Initialize Go module: go mod init github.com/org/hrms-backend
    2. Add dependencies: pgx/v5, sqlc or gorm, golang-migrate
    3. Configure DB connection pool (pgxpool) with env-based config
    4. Generate typed SQL code with sqlc from migration files
    5. Write repository interfaces for each module
    6. Unit-test DB layer with testcontainers-go

FastAPI AI Backend Integration:
    1. Set up Python virtual environment + requirements.txt
    2. Add dependencies: asyncpg, SQLAlchemy 2.x, pgvector-python
    3. Configure async DB session factory
    4. Implement repository classes for face_embeddings & kb_chunks
    5. Test vector insert and cosine similarity query
    6. Set up Alembic for AI service migrations (separate schema)

Directory Structure:
    /backend-go/
    ├── cmd/server/main.go
    ├── internal/
    │   ├── config/
    │   ├── db/            ← connection pool, migrations runner
    │   ├── repository/    ← DB access layer per module
    │   ├── service/       ← business logic
    │   ├── handler/       ← HTTP handlers (Gin/Fiber)
    │   └── middleware/    ← auth, logging, rate-limit
    ├── pkg/
    ├── migrations/
    └── go.mod

    /backend-ai/           ← FastAPI service
    ├── app/
    │   ├── api/routes/
    │   ├── core/config.py
    │   ├── db/session.py
    │   ├── models/        ← SQLAlchemy ORM models
    │   ├── services/      ← face recognition, RAG pipeline
    │   └── schemas/       ← Pydantic request/response models
    ├── requirements.txt
    └── Dockerfile

────────────────────────────────────────────────────────────────────────────────
PHASE 5: FACE RECOGNITION SYSTEM (Week 8–10, FastAPI)
────────────────────────────────────────────────────────────────────────────────
Deliverables:
    □ Face enrollment endpoint (stores embedding in pgvector)
    □ Face verification endpoint (cosine similarity search)
    □ Liveness detection
    □ Anti-spoofing safeguards

Tasks:
    1. Set up InsightFace or DeepFace in FastAPI
    2. Implement /ai/v1/face/enroll:
       - Accept image → detect face → compute 512-d embedding
       - Store in face_embeddings with pgvector
    3. Implement /ai/v1/face/verify:
       - Accept image → compute embedding
       - Run cosine similarity search: SELECT ... ORDER BY embedding <=> query_vec LIMIT 1
       - Return matched employee + confidence score
    4. Implement liveness detection (eye-blink / model-based)
    5. Add confidence threshold check (reject if score < 0.75)
    6. Wrap with FastAPI dependency injection and auth token validation
    7. Write integration tests with sample face dataset
    8. Performance benchmark: target < 2s per verification

────────────────────────────────────────────────────────────────────────────────
PHASE 6: FASTAPI ↔ GO BACKEND INTEGRATION (Week 10–11)
────────────────────────────────────────────────────────────────────────────────
Deliverables:
    □ Secure internal service communication
    □ Go attendance module calls FastAPI for face verification
    □ Go recruitment module calls FastAPI for resume parsing
    □ Response handling and fallback logic in Go

Tasks:
    1. Define shared internal API contract (OpenAPI spec)
    2. Implement service-to-service authentication (shared secret / mTLS)
    3. Go HTTP client wrapper for FastAPI calls (with retry + timeout)
    4. In Go attendance handler:
       - Receive image upload → call FastAPI /face/verify
       - On success → create attendance record → return response
    5. In Go recruitment handler:
       - Receive resume upload → call FastAPI /resume/parse
       - Store structured candidate data
    6. Implement circuit breaker pattern (go-resilience)
    7. Add fallback: if AI service is down, allow manual attendance
    8. Integration tests: Go service → FastAPI → response
